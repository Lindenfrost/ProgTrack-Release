# Proposed canonical data dictionary and entity map

This is a design proposal, not a live schema. Names are semantic; Phase 2B may
adapt physical table names while preserving the approved boundaries.

## Identity rules

### Stable internal IDs

- An animal's IPID is its immutable primary key and the animal foreign key
  across all services and plugins.
- IPID is assigned once during initial creation, after validation, and can
  never be changed, regenerated, or reused.
- Name, full birth date, species, and immutable Herkunftseinrichtung form the
  animal identity block with IPID. Herkunftseinrichtung uses the existing
  animal field `origin`; no additional animal field is introduced. IPID has the canonical form
  `name | species | DD.MM.YYYY | origin`. `origin` is the controlled
  manager-maintained animal-origin value already used by ProgTrack, not a
  centrally issued identifier.
- IPID generation uses all four identity fields. Once the animal has been
  created, neither IPID nor any source field can be edited by any account,
  including Lord.
- Authorized Lord, Master, or Manager users may maintain future choices in the
  controlled origin catalogue. Catalogue changes never rewrite an existing
  animal's stored `origin`; a historical value remains valid for that animal
  even when it is no longer offered for new animals.
- A wrongly finalized identity is not edited, superseded, merged, aliased, or
  automatically repaired in Phase 2B. An authorized user deletes the erroneous
  animal through the normal audited workflow and creates a correct animal.
  Dependent measurements, relationships, assignments, documents, folders, and
  plugin records are not transferred automatically.
- Imported animals retain their immutable origin block. A full IPID
  collision therefore means the package refers to the same canonical animal
  or contains invalid conflicting data; it is resolved idempotently or
  quarantined, never by renaming the animal.
- If an imported origin is not yet in the local controlled catalogue, an
  authorized Lord, Master, or Manager must explicitly add/approve it during
  import preview before the animal can be created.
- The deterministic disposable example-origin cleaning was completed on
  2026-07-28 for all 227 animals and the controlled catalogue. Phase 2B does
  not repeat or reinterpret it; four-block IPID creation consumes the cleaned
  stored `origin`. This was sample-data editing, not production migration or a
  runtime identity feature.
- Every installation-created durable non-animal record receives an immutable
  facility-owned record ID generated by the shared data layer.
- Every facility-owned record ID is namespaced by a manager-defined
  originating-facility tag, for example `<facility_tag>:<uuid>`. There is no
  central allocation service. Once used in an ID, the tag and complete ID are
  immutable. Raw untagged per-facility counters are forbidden.
- Animal references use IPID. Project, user, cage, sample, document, event, and
  other installation-created references use facility-owned record IDs.
- Global semantic IDs are installation-independent and never facility-tagged.
  They include permissions (including internal-only permissions), built-in
  animal roles, plugin keys, schema/package IDs, statuses, event and
  relationship types, units, analytes, specimens, standardized taxonomy IDs,
  and other constants explicitly frozen as application protocol vocabulary.
- Custom roles, custom jobs, and other installation-created configuration
  definitions are facility-owned records. Their visible labels and local
  semantic keys are not portable foreign keys.
- The current generated animal `id`, chip number, and external-system
  identifiers are typed alternate identifiers and are not database keys.
- Labels and usernames are never foreign keys.

The entity tables use `facility-owned record ID` deliberately. `UUID` refers
only to its collision-resistant component and is not a blanket synonym for all
non-animal keys.

### Roles

Animal role IDs remain:

`egg_cell_donor`, `surrogate`, `sperm_donor`, `offspring`,
`partner_animal`, `breeding_animal`, `experimental_animal`, and `unknown`.

Localized labels are presentation resources. Built-in role IDs are global
semantic IDs. Custom roles use facility-owned record IDs plus a local semantic
key separate from the label. User access roles remain `lord`, `master`,
`animal_welfare_officer`, `user`, and `guest`; custom job bundles are
facility-owned configuration.

## Common record fields

Facility-owned durable records should normally expose:

| Field | Meaning |
| --- | --- |
| `id` | immutable `<facility_tag>:<uuid>` facility-owned record ID |
| `facility_tag` | immutable originating namespace embedded in `id` |
| `revision` | monotonically increasing optimistic-concurrency version |
| `created_at`, `created_by_user_id` | creation provenance |
| `updated_at`, `updated_by_user_id` | latest mutation provenance |
| `source_system`, `source_record_id` | import provenance/idempotency key |
| `archived_at` or `status` | non-destructive lifecycle where appropriate |

Event/history rows are append-only and use event time plus actor/correlation
fields instead of being overwritten.

Animals instead use immutable IPID and never carry a second primary key.
Global semantic/reference definitions use their frozen protocol IDs and do not
require `facility_tag`. Mutable controlled catalogues and custom definitions
are facility-owned configuration records even when individual built-in
vocabulary IDs remain global.

## Core animal entities

| Entity | Required semantic fields | Current source |
| --- | --- | --- |
| `animal` | immutable four-block IPID, immutable name/species/full birth date/origin, record kind (`operational`, `heritage_only`), sex, genotype, active/archived/deceased/departed state | core animals/archived plus Heritage-only animals |
| `animal_identifier` | animal IPID, identifier type (`public_id`, `chip`, external system), value, issuer, validity | `id`, `chip_nr`, additional external IDs |
| `animal_role_assignment` | animal IPID, internal role ID, valid-from/to, primary flag | `rolle`; future history |
| `animal_relationship` | subject animal IPID, related animal IPID, relationship type, valid time, provenance | four parent fields, mating/partner fields |
| `animal_lifecycle_event` | facility-owned event ID, animal IPID, global semantic event type, date/time, reason, recipient, actor | lifecycle fields and `lifecycle_events` |
| `animal_status_event` | animal IPID, status type, start/end, reason/source | sick/abnormal/experiment/death/departure fields |
| `animal_limit` | animal IPID, semantic limit type, value | `max_*`, recovery settings where animal-specific |

Relationship types include at least `genetic_mother`, `genetic_father`,
`surrogate_mother`, `surrogate_father`, `mate`, and `partner`. Direction and
reciprocity are defined by type rather than duplicated free text.

## Non-durable measurement-import DTOs

These structures are service transfer objects, not database entities:

| DTO | Required fields |
| --- | --- |
| `measurement_import_plan` | plan/correlation ID, actor, measurement type, source fingerprint, classified-at, full-file row decisions, aggregate counts, unknown identifiers, expiry/revalidation token |
| `measurement_import_row_decision` | source row locator, parsed Animal ID/IPID and Sample ID separately, resolved existing animal IPID if any, status (`existing`, `unknown`, `archived`, `ambiguous`, `invalid`, `duplicate`, `permission_rejected`), reason, normalized measurement payload |
| `measurement_import_result` | plan/correlation ID, committed/rejected state, imported/skipped/invalid/duplicate/newly-invalid counts, identifiers/reasons, committed batch IDs if batching is required |

The preview and commit consume the same immutable plan. Commit revalidates it
transactionally. MeasurementService accepts only resolved existing animal
IPIDs; MeasurementImportService cannot call AnimalService creation or create a
placeholder, folder, sample owner, or incomplete identity record.

## Ownership and service boundaries

- `AnimalService`: animal identity, role, relationships, lifecycle/status.
- `MeasurementService`: measurements and sample linkage.
- `ProjectService`: projects, visibility, user/animal assignments.
- `HousingService`: hierarchy, occupancy, movement, inspections.
- `MedicalService`: medical issues/entries and clinical status.
- `SampleService`: sample/aliquot inventory and storage.
- `ReproductionService`: Flow/embryo/donation/transfer domain.
- `PlanningService`: Surgery plan/calendar records.
- `ReportService`: report queries, manual overrides, exports.
- `DocumentService`: all managed payload metadata/lifecycle.
- `SecurityService`: users, roles/jobs, permissions, sessions.
- `LockService`: generic visible edit leases.
- `InterchangeService`: export, preview, validation, import.
- `MeasurementImportService`: full-file operational workbook classification,
  preview, existing-animal-only commit, result and operation audit.
- `ConfigurationService`: facility namespace, institution branding, custom
  roles/jobs, and versioned shared configuration.

Plugins may own domain behavior and UI, but these shared services own durable
storage and invariants.
